# coding-pm - 项目同步管理 Skill

这是一个四段式 skill，管理项目的开始、同步、审计和结束。每次被触发时，先判断用户说的是哪个阶段关键词，然后执行对应操作。

---

## 总览

| 关键词 | 阶段 | 做什么 |
|--------|------|--------|
| **开工** | 🚀 项目开始 | 扫描规则文档（有则用，无则提问创建 AGENTS.md）→ 创建 app/design/docs → 报告就绪 |
| **同步一下** | 🔄 进行中同步 | 读代码 → 创建/同步 ui-components.html（CSS变量/字体/组件状态/SSE/事件绑定/状态流转/动画/响应式）→ 增量更新 docs/README |
| **审计验收**（完整4字） | 🔍 项目审计 | 先检查 docs/ 和 design/ui-components.html 是否与代码同步 → 不同步则报错并说明哪里不同步 → 同步则根据文档对前后端架构层代码逐项审计（规则来源/对应文件/验收方式/实际结果/是否通过）→ 根目录出审计报告 |
| **收尾** | 🏁 项目结束 | 全量重写 docs/ + design/ → 版本 v1.0 → 产出 PRD.md + SPEC.md + README.md + ui-components.html → 详细到可复现 |

**目录结构：**
- `app/` → 项目代码相关的文件
- `design/` → UI、UX、组件或视觉参考设计稿文件
- `docs/` → PRD（产品需求）、SPEC（技术规格）、README 等开发或项目规范文档

---

## 第一阶段：「开工」—— 项目开始

当用户说出"开工"或类似的"开始项目"意图时，执行以下步骤：

### 1. 加载项目规则文档

扫描当前项目根目录，检查是否存在以下已知的规则文档文件名（按优先级从高到低检查）：

| 优先级 | 文件名 | 说明 |
|--------|--------|------|
| 1 | `.claude.md` | Claude 项目规则（隐藏文件） |
| 2 | `CLAUDE.md` | Claude 项目规则（大写） |
| 3 | `AGENTS.md` | Agent 规则（大写） |
| 4 | `project-rules.md` | 项目规则 |
| 5 | `.cursorrules` | Cursor 规则 |

然后按两种分支处理：

#### 分支 A：找到了规则文档（优先级最高的那个）

- **显式告诉用户找到的是哪个文件**
- 加载其内容并严格遵守其中的规则
- 直接进入第 2 步

#### 分支 B：没有找到任何规则文档

**一次只问一个问题**，等用户回答了再问下一个。问完所有问题后，在项目根目录创建 `AGENTS.md`，把用户回答的内容整理成规则文档，并严格遵守。

**原则**：先了解你这个人（角色、能力、习惯、原则），再了解项目（做什么、给谁用）。所有问题**一次只问一个**，你回答完再问下一个。

**要问的问题（按顺序，一次一个）：**

| 顺序 | 归属 | 问题 | 为什么问 |
|------|------|------|----------|
| 1 | 关于你 | **你是什么角色？**（产品经理、设计师、开发者、运营？） | 决定用什么语气沟通，也影响后续问题的方向 |
| 2 | 关于你 | **你的技术水平怎么样？**（完全不懂、能看懂、熟练、专家？） | 决定是否用技术术语，是否要帮你推荐技术方案 |
| 3 | 关于你 | **你习惯用什么语言沟通？**（中文/英文，正式/随意？） | 设定沟通风格 |
| 4 | 关于你 | **你做事有什么核心原则？**（比如：先想清楚再动手、不搞花架子、简洁至上？） | 这些是规则文档最重要的内容 |
| 5 | 关于你 | **有什么工作纪律要我遵守的？**（比如：改完代码必须验证、不能绕开问题、不碰无关代码？） | 写进规则文档，每次调用都遵守 |
| 6 | 关于你 | **有什么特别不让我做的？**（比如：别自作主张改已有的代码、别用我不认识的技术？） | 明确边界和禁区 |
| 7 | 关于项目 | **这个项目是做什么的？一两句话描述** | 项目定位和核心目标 |
| 8 | 关于项目 | **项目的目标用户是谁？** | 产品给谁用的 |

> **重要**：一次只问一个问题！用户回答完再问下一个。务必严格按照表格顺序逐个提问。

所有问题问完后，把回答整理成 `AGENTS.md` 文件。

**生成的 `AGENTS.md` 参考格式：**

```markdown
# 项目规则

## 关于你
- **角色**：[用户回答]
- **技术水平**：[用户回答]
- **沟通语言**：[用户回答]

## 核心原则
[用户回答的原则内容]

## 工作纪律
[用户回答的纪律和要求]

## 边界
[用户回答的禁区]

## 项目信息
- **项目名称**：[根据回答确定]
- **项目描述**：[用户回答]
- **目标用户**：[用户回答]
```

### 2. 检查/创建目录结构

确保以下三个目录存在（不存在则创建）：

```
项目根目录/
├── app/     # 项目代码相关的文件
├── design/  # UI、UX、组件或视觉参考设计稿文件
└── docs/    # PRD（产品需求）、SPEC（技术规格）、README 等开发或项目规范文档
```

### 3. 通知用户

向用户报告：
- ✅ 规则文档状态（找到哪个文件 / 已创建 AGENTS.md）
- ✅ 目录结构状态（已存在/已创建）
- ✅ 项目已就绪，可以开始工作

---

## 第二阶段：「同步一下」—— 项目进行中同步

当用户说出"同步一下"或类似的"更新文档"意图时，执行以下步骤：

### 1. 读取当前项目状态

- 读取 `app/` 目录下的所有代码文件，了解当前实现了什么功能
- 读取 `design/` 目录下已有的设计文件（包括 ui-components.html 如果存在）
- 读取 `docs/` 目录下已有的文档（含 README.md）
- 读取项目规则文档（同第一阶段扫描方式）

### 2. 对比分析

理解当前代码实际实现了什么，与现有文档对比找出：
- 新增了哪些功能但文档没写
- 哪些 UI/UX 已经变了但设计文档没更新
- 技术栈是否有变化
- 用户流程是否有调整

### 3. 创建/同步更新 ui-components.html

这是本阶段的核心任务。目标是：在 `design/` 目录创建一个名为 `ui-components.html` 的 HTML 文件（如果已存在则同步更新），把当前项目的**所有 UI、UX 和组件细节全部写进去**，标准是**别人打开这个 HTML 就能 1:1 复刻出完全一样的外观和交互**。

**不是只写下面列的这些条目**——下面这个表是参考框架，告诉你从哪些维度去写。实际项目中有什么就写什么，把所有能看到的、能交互的都写进去：

| 维度 | 写什么 |
|------|--------|
| **CSS 变量表** | 项目用到的所有 CSS 自定义属性（颜色、字体、间距、圆角等），展示变量名、值和用途 |
| **字体示范** | 项目中使用的字体族、字号层级、字重、行高，附实际渲染示例 |
| **布局规范** | 页面布局结构、网格系统、间距体系，附示意图或文字说明 |
| **所有组件** | 每个组件的名称、用途、代码结构，**每种状态都要演示**（默认、悬停、激活、禁用、加载、空态、错误态） |
| **SSE 协议** | 如果项目使用了 Server-Sent Events，说明事件流格式、连接方式、重连策略 |
| **模板结构** | 页面/组件的 HTML 模板骨架说明 |
| **事件绑定表** | 所有交互事件（click、change、submit、scroll 等）及其绑定元素、触发条件和处理逻辑 |
| **状态流转矩阵** | 页面/组件的状态变化关系，什么操作触发什么状态转换 |
| **动画汇总** | 项目中用到的所有过渡动画、关键帧动画，附持续时间和缓动函数 |
| **响应式断点** | 各断点阈值以及对应布局/组件变化 |

HTML 页面要求：
- 自包含、可直接在浏览器打开（无需服务器）
- 使用项目本身的 CSS 变量和设计风格做展示
- 结构清晰、视觉美观，方便设计师和开发者查阅
- 新增的组件加上、改动的更新、已不存在的标记废弃并写明原因

### 4. 同步更新 docs/ 目录

根据实际代码情况，**增量更新** `docs/` 下的文档：

> **新增的内容** → 文档中补上
> **修改的内容** → 文档中更新
> **已不存在的内容** → 文档中标记为「🚫 废弃」并写明原因
> **没变的内容** → 保持原样不动

具体操作：
- 读出现有文档，对比当前代码，找出变化
- 代码新增的功能 → 文档中加上
- 代码改动的地方 → 文档中更新
- 代码中已不存在的东西 → 文档对应位置标记废弃并写明原因（如「用户反馈该功能无实际需求，v1.0 中移除」）
- 没变的不动，保持文档进度与实际代码一致

### 5. 通知用户

向用户报告：
- ✅ `design/ui-components.html` 已创建或已同步更新
- ✅ 同步更新了哪些 docs/ 文档
- ✅ 当前项目进度概要

## 第三阶段：「审计验收」—— 项目审计与验收

当用户说出"审计验收"（必须是完整的4个字）时，执行以下步骤：

> **重要前提**：本阶段是"质量把关"环节，必须在文档和代码同步的前提下进行。如果不同步，先叫用户做"同步一下"，不做完不同步审计。

### 第1步：检查文档与代码是否同步

这是审计的前置检查。如果不通过，直接中断审计流程。

- 读取 `app/` 目录下的所有代码文件
- 读取 `docs/` 下的所有文档（PRD.md、SPEC.md、README.md 等）
- 读取 `design/ui-components.html`
- 对比文档描述和实际代码实现，检查是否一致

**同步检查清单：**

| 检查项 | 内容 |
|--------|------|
| 🔍 docs/ 文档与代码 | PRD 中的功能列表是否与代码实现一致？SPEC 中的技术描述是否准确？README 中的说明是否过时？ |
| 🔍 design/ui-components.html 与代码 | HTML 中描述的组件、状态、样式变量、交互事件是否与实际代码一致？ |
| 🔍 新增/删除的功能 | 代码中有没有新增但文档没写的功能？代码中已经删除但文档还保留的内容？ |

### 第2步：处理不同步情况

**如果发现不同步**：

立即中断审计流程，向用户汇报：

> ⛔ **审计中断：项目文档与代码不同步**
>
> 以下内容不同步：
> - ❌ （文档中写了但代码中不存在 / 代码中有但文档没写 / 描述不一致）—— 具体说明位置
> - ❌ ...
>
> 请先执行「同步一下」更新文档，再重新执行审计验收。

**不要在审计阶段自动同步文档**——只汇报问题，让用户决定是否先同步。

### 第3步：同步通过，执行审计

如果所有检查项都通过（文档与代码一致），则进入正式审计阶段。

**审计范围**：根据 `docs/` 下的所有文档（PRD.md、SPEC.md、README.md）和 `design/ui-components.html` 的描述，对前后端架构层代码做逐项审计和验收。

**每项审计必须包含以下五个要素：**

| 要素 | 说明 |
|------|------|
| 📐 **规则来源** | 这条验收规则来自哪个文档的哪个章节？例如：SPEC.md → 技术架构章节 → API 接口规范 |
| 📁 **对应文件** | 被审计的具体文件路径（如 `app/backend/src/routes/todo.js`） |
| 🔬 **验收方式** | 怎么验证的？手动代码审查、静态分析、运行测试等 |
| 📊 **实际结果** | 检查后实际看到的状态（如"实现了3个接口中的3个，接口路径与文档一致"） |
| ✅ **是否通过** | 通过 / 不通过（不通过时需写明具体问题） |

**审计维度（至少覆盖以下方面）：**

| 审计维度 | 参考文档 | 审计内容 |
|---------|---------|---------|
| 🏗️ **架构一致性** | SPEC.md → 技术架构 | 代码目录结构是否与文档描述的架构一致？前后端分层是否按文档设计？模块间关系是否符合文档？ |
| 🛠️ **技术栈合规** | SPEC.md → 技术栈 | 实际使用的技术栈（框架、库、数据库、第三方服务）是否与文档一致？版本是否匹配？ |
| 🧩 **组件完整性** | design/ui-components.html | 文档中描述的每个组件是否在代码中实现？每种状态（默认/悬停/激活/禁用/加载/空态/错误态）是否都正确处理？ |
| 🔗 **API 接口** | SPEC.md → 前后端通信 | 文档定义的 API 接口是否都在代码中实现？请求方法、路径、参数、响应格式是否一致？ |
| 🔄 **用户流程** | SPEC.md → 用户流程 | 用户从进入到完成核心任务的完整流程在代码中是否走通？异常流程是否处理？ |
| 🎨 **样式一致性** | design/ui-components.html → CSS变量/布局 | 代码中使用的 CSS 变量、布局、字体、间距是否与设计文档一致？ |
| 📡 **SSE 协议** | design/ui-components.html → SSE协议 | 如果项目用了 SSE，事件格式、连接方式、重连策略是否按文档实现？ |
| ⚡ **交互/动效** | design/ui-components.html → 事件绑定/动画 | 交互事件、动画效果是否按文档实现？行为是否符合预期？ |

### 第4步：产出审计报告

在**项目根目录**下创建一个名为 `audit-report.md` 的文件，作为本次审计的正式报告。

**审计报告格式示例：**

```markdown
# 项目审计验收报告

**审计日期**：2026-06-28
**审计依据**：docs/PRD.md + docs/SPEC.md + design/ui-components.html
**审计范围**：前后端架构层代码

---

## 审计结果总览

| 审计维度 | 总项数 | 通过 | 不通过 | 通过率 |
|---------|--------|------|--------|--------|
| 架构一致性 | N | N | N | N% |
| 技术栈合规 | N | N | N | N% |
| 组件完整性 | N | N | N | N% |
| API 接口 | N | N | N | N% |
| 用户流程 | N | N | N | N% |
| 样式一致性 | N | N | N | N% |
| SSE 协议 | N | N | N | N% |
| 交互/动效 | N | N | N | N% |
| **总计** | **N** | **N** | **N** | **N%** |

---

## 逐项审计明细

### 审计项 1：
- **规则来源**：说明来源文档和章节
- **对应文件**：被审计的文件路径
- **验收方式**：怎么验的
- **实际结果**：看到的结果
- **是否通过**：✅ 通过 / ❌ 不通过

### 审计项 2：
- ...

---

## 问题清单（仅不通过项）

| 序号 | 问题描述 | 严重程度 | 建议修复方案 |
|------|---------|---------|-------------|
| 1 | ... | 高/中/低 | ... |

---

## 审计结论

总体评价：文档与代码同步情况 / 项目代码质量 / 最终结论（通过/有条件通过/不通过）
```

### 第5步：通知用户

向用户报告：
- ✅ 同步检查结果（通过/未通过——如未通过已中断审计）
- ✅ 审计总览（审计了多少项、通过率）
- ✅ 审计报告已生成在项目根目录 `audit-report.md`
- ✅ 如有不通过项，列出关键问题

---

## 第四阶段：「收尾」—— 项目结束，全量重写文档

当用户说出"收尾"或类似的"项目结束"意图时，执行以下步骤：

这是整个 skill 最重要的阶段。目标是：**完全重写 docs/ 和 design/ 下所有文件，把当前版本定为 v1.0，详细到别人拿到就能原样复现。**

需要完整产出的内容包括：技术架构、UI/UX 组件、面对的用户群体、用户流程、用户交互、**验收标准**、技术栈、前后端等，把所有技术问题和流程写详细。

### 执行顺序

#### Step 1: 全面读取项目

- 递归读取 `app/` 下所有代码文件
- 读取 `design/` 下已有的设计参考
- 读取项目规则文档
- 理解完整的项目范围

#### Step 2: 全量重写 docs/ 目录

创建/重写以下文档文件（每个文件都必须是完整的、可独立阅读的）：

**`docs/PRD.md`** — 产品需求文档
- 项目背景：要解决什么问题？为什么做？
- 目标用户群体：产品的用户是谁？画像描述
- 核心功能列表：做什么功能？优先级排序
- 验收标准：怎么判断功能做好了？每个核心功能对应的验收条件和通过标准
- 成功指标：怎么衡量做得好不好？

**`docs/SPEC.md`** — 技术规格文档（这是最核心的文件，要写得最详细）
- **技术架构**：整体架构图（文字或 mermaid）、前后端分层、数据流/请求流、模块间关系、部署架构
- **技术栈**：前端（框架、UI 库、构建工具、状态管理）、后端（语言、框架、数据库、缓存、消息队列）、第三方服务/API 集成、开发工具链，**每个选型要写为什么选它**
- **用户流程**：用户从进入产品到完成核心任务的完整流程、每个页面的入口/出口、关键交互节点的操作步骤、异常流程处理

## 重要原则

1. **准确性优先**：所有文档内容必须基于实际代码和设计，不得凭空编造。如果不确定某个细节，明确标注"待确认"而非猜测。
2. **可复现性**：收尾阶段的文档标准是——一个开发者拿到这些文档，不需要再问问题就能做出完全一样的产品。所以每个技术决策都要写为什么，每个组件都要写全状态。
3. **找到什么用什么**：规则文档扫描时找到哪个用哪个，告诉用户找到了哪个。不强制要求必须存在某个文件。
4. **尊重已有内容**：开工阶段不删除/不改动已有代码和文件。同步阶段增量更新，不随意删除。收尾阶段才全量重写。
